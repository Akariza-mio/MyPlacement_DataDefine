## 1. 我们到底在做什么

可以把芯片想象成一块画板，把芯片上的“单元”想象成大小不同的小矩形。单元之间通过“管脚”连接；管脚就是单元上接线的位置。“网络”是一组需要连在一起的管脚，不是计算机网络。

布局程序要给小矩形安排位置。其中，一部分单元允许移动，另一部分已经指定了位置，必须保持不动。

“初始布局”是先给后面的优化程序安排一个起点。本阶段的要求是：

- 所有可移动单元都获得有效位置，而且整个矩形都在指定的布局区域内。
- 固定单元保持原位置。有些固定端子本来就在区域外，不能为了让它进入区域而移动它。
- 单元之间允许重叠。消除重叠、对齐到摆放行等工作属于后面的全局布局和合法化阶段。
- 运行结果可以保存、重新检查，并用于比较不同方法。

因此，“没有重叠”和“线长一定最短”都不是今晚随机布局的通过条件。

## 2. 三种方法分别负责什么

| 方法 | 用普通话解释 | 主要编码内容 | 开发安排 |
| --- | --- | --- | --- |
| 随机布局 | 给每个可移动小矩形随机找一个放得下的位置 | 计算可选范围，生成坐标，保留固定位置 | 正式接入和验收已完成 |
| 聚类驱动布局 | 先把联系紧密的单元分成小组，再安排每组和组内的位置 | 计算连接强弱，合并小组，限制小组大小，安排位置 | 后续阶段 |
| 二次方程解析布局 | 根据连接关系列出一组数学方程，用求解结果安排位置 | 考虑管脚偏移和固定位置，反复更新连接权重并解方程 | 后续阶段 |

三种方法使用同一套输入和输出方式。以后比较时，要让它们各自从同一份原始电路开始，不能把一种方法已经移动过的坐标直接交给另一种方法，再声称是公平比较。

聚类的方法还需要确定“怎样计算连接强弱、何时停止合并、每组放在哪里”；这些规则尚未实现，后续编码前单独补充。解析方法需要多次更新权重和求解，不能把“只解了一次方程”当作完整实现。

## 4. 最容易出错的几件事

### 4.1 左下角和中心是两个位置，不能混用

`.pl` 保存的是单元的左下角；现有布局代码中的 `center` 表示单元中心。队友解析器目前直接把文件中的左下角写进 `center`，所以读完后必须转换一次。

例如，一个单元宽20、高10，文件中左下角是 `(100, 200)`：

```text
读入文件：左下角 = (100, 200)
程序内部：中心   = (100 + 20/2, 200 + 10/2) = (110, 205)
保存文件：左下角 = (110 - 20/2, 205 - 10/2) = (100, 200)
```

固定单元也要做这次转换。这不代表移动了它，只是换了一种记录同一位置的方式。转换必须在新数据加载后只执行一次；不能每次调用布局算法都再加半宽、半高。

### 4.2 “中心在区域内”不代表“整个单元在区域内”

假设区域宽100，单元宽20。如果把中心放在横坐标5，单元左边就到了-5，已经越界。

因此，这个单元的中心横坐标只能在 `[10, 90]` 内选择。对于一般区域，中心允许范围是：

```text
横坐标：区域左边界 + 单元宽度/2，到 区域右边界 - 单元宽度/2
纵坐标：区域下边界 + 单元高度/2，到 区域上边界 - 单元高度/2
```

这是现有随机布局已经采用的做法。单元比区域还大时，要明确报错，不应把它强行缩小。

### 4.3 固定状态要核对，不能只看列表名称

布局时以 `isFixed` 判断能不能移动。`Nodes` 和 `Terminals` 是数据库中的两个列表名称，不应单靠它们决定是否移动。

队友的 `.pl` 读取函数没有保留方向和 `/FIXED`。读入整理层要核对这些信息与 `.nodes` 分类是否一致；遇到矛盾要报错，不能悄悄选择一边。当前先支持已经验证的 `N` 方向，也就是不旋转；其他方向明确拒绝，等方向规则补齐后再扩展。

`thin1` 中固定单元 `o211025` 的文件左下角是 `(6240,22)`，宽72、高432，程序内中心应为 `(6276,238)`。随机布局后导出，它仍应回到文件中的 `(6240,22)`。

### 4.4 布局区域要从行数据计算

从 `.scl` 中找到所有摆放行的最左、最下、最右、最上位置，得到 `CoreRegion`。程序要计算这些值，不能根据电路名称把答案写死。

行的顶部是“行底部 + 行高”，不是行底部本身。当前三个数据集的格点宽度和间距相同，可使用已核查的行范围；以后若遇到一行包含多个分段、格点宽度与间距不同等情况，需要补充支持或明确拒绝，不能假装已经兼容。

### 4.5 读到数据后还要检查，不能只看“解析完成”提示

队友读取器在文件打不开时主要打印错误，不能保证调用方自动停止。因此，正式入口还要检查文件是否存在、记录是否完整、单元名是否重复、数量是否相符、坐标和尺寸是否有效。对坏输入应停止运行并给出具体原因，不能继续输出看似成功的布局结果。

还要处理几个公共细节：面积按“宽×高”计算；同一单元不能在列表中重复出现；后续求解方程时为可移动单元重新编号，不假定旧编号正好连续。同一个单元的多个管脚连到同一网络时，统计“单元之间的联系”要避免重复计数，但不能删除实际存在的管脚。

## 5. 今晚要完成的运行流程

今晚的成果是一条可以重复执行的流程：

```text
指定电路目录、名称、随机种子和输出位置
    ↓
检查输入文件，调用队友的解析器
    ↓
整理坐标、方向和固定状态，计算布局区域，核对数据
    ↓
调用已有 randomPlace
    ↓
检查可移动单元有没有越界、固定单元有没有变化
    ↓
调用已有 writePl 保存结果，输出运行统计
```

正式入口应接收用户给出的路径，不再依赖 `myplace_main.cpp` 中写死的 `./test_data/adaptec1`。运行失败应返回失败状态，并说明具体文件或单元；成功报告只能在检查和保存都完成后输出。

入口已经支持 `--input-dir`、`--benchmark`、`--method random`、`--seed`、`--output` 和可选的 `--report`。省略种子时采用42；省略报告路径时，报告保存为“输出文件名 + .report.json”。完整命令见第12节。

## 7. 怎样判断随机布局真的完成了

### 7.1 小例子：检查规则本身

| 检查 | 通过标准 |
| --- | --- |
| 区域不从原点开始 | 仍按实际边界放置，没有偷偷使用 `(0,0)` |
| 固定单元在区域外 | 位置和固定标记保持不变 |
| 相同种子重复运行 | 相同环境、输入和顺序下结果一致 |
| 换一个种子 | 在位置选择有余地的例子中能观察到不同结果；不要求任何输入都必然不同 |
| 单元刚好填满区域 | 可以放置，中心唯一；多个这样的单元允许重叠 |
| 单元比区域还大、区域无效 | 明确失败，不能先移动一部分再报输入错误 |
| 名称重复、指针重复或缺少必要文件 | 加载或检查阶段明确失败 |
| 非 `N` 方向或固定信息矛盾 | 明确提示尚不支持或数据不一致 |
| 保存后重新读取 | 单元齐全，固定位置和标记保留，坐标转换正确 |
| 输出位置不可写 | 返回失败，不能报告保存成功 |

### 7.2 真实电路：检查完整流程

三个数据集按 `thin1 → adaptec1 → adaptec4` 的顺序运行，每个都要检查全部单元，不只抽看几行输出。

完成标准：

- 输入、内存数据、输出文件中的单元数量一致；没有丢失、增加或重复名称。
- 所有可移动单元的矩形都在区域内，所有坐标都是有效数字。
- 所有固定单元的位置、固定标记保持正确，不要求固定单元进入区域。
- 用相同种子在同一环境重跑，坐标结果一致。
- 检查程序独立读取输出 `.pl` 再核对，不能只让保存函数自己说“成功”。
- 有可复制的构建、运行命令，正常返回成功，失败返回失败。

随机布局的“小函数写好”不等于以上全部完成。今晚要验收的是正式工程中的完整流程；测试目录里的隔离演示只能作为接入参考。

### 7.3 保存哪些统计

每次正式实验至少保存：电路名称、解析源码版本、运行环境、种子、区域边界、可移动与固定单元数、越界数量、固定位置变化数量、输入和输出数量、输出路径。

还要记录布局计算耗时和 HPWL。耗时只统计算法安排位置的过程，并与读文件、保存文件的时间区分。HPWL 是常用的接线长度估计：对一个网络，找到所有管脚最左、最右、最下、最上的位置，用“横向跨度 + 纵向跨度”作为该网的估计线长，再把各网相加。它不是实际布线长度，也不是随机布局必须降低的指标。

计算 HPWL 要使用“单元中心 + 管脚相对中心的偏移”，固定单元的管脚也要参加；先用能手算的小例子验证统计公式。随机布局不需要读取连接关系才能挑位置，但为后面三种方法共用评测，本项目仍读入 `.nets`。

大型电路的全部重叠对统计和正式布局图片留到后续统一比较时补充，不作为今晚结束随机编码的必需条件。

## 12. 已完成版本怎样运行

以下命令均以本机实际验证路径为准。若换电脑，只需按实际安装位置调整工具和电路路径；正式程序不依赖本机测试目录中的文件来完成构建。

### 12.1 Windows PowerShell：构建并运行一个电路

```powershell
Set-Location -LiteralPath 'D:\综合设计III参考资料\任务4参考\MyPlacement_DataDefine'
$taskCmake = 'D:\Program Files\Microsoft Visual Studio\18\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe'
$taskNinja = 'D:/Program Files/Microsoft Visual Studio/18/Community/Common7/IDE/CommonExtensions/Microsoft/CMake/Ninja/ninja.exe'

& $taskCmake --build build/random-windows-ninja --parallel 4
.\build\random-windows-ninja\myplace.exe --input-dir '..\..\任务2参考\BookShelf格式的解析\thin1' --benchmark thin1 --method random --seed 42 --output test_data/random_results/windows/thin1_seed42.pl
```

正常运行会打印 `SUCCESS`，并生成位置文件和同名附加 `.report.json` 的报告。也可以运行 `myplace.exe --help` 查看参数。参数或数据不正确时打印 `ERROR` 并返回非零状态；输入文件不能被指定为输出位置，结果与报告也不能使用同一文件。

### 12.3 一次重跑三个真实电路的独立验收

在Windows的上述工程目录中：

```powershell
$taskPython = 'C:\Users\WANG\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $taskPython -X utf8 test_data/run_random_acceptance.py --exe build/random-windows-ninja/myplace.exe --data-root '../../任务2参考/BookShelf格式的解析' --results-dir test_data/random_results/windows
```

在Ubuntu的上述工程目录中：

```bash
python3 test_data/run_random_acceptance.py --exe build/random-linux/myplace --data-root '../../任务2参考/BookShelf格式的解析' --results-dir test_data/random_results/linux
```

脚本先检查命令行错误与中文路径，再让每个电路使用种子42独立运行两次，并调用 `check_random_output.py` 重新读取输出。核对名称、固定位置、方向、严格边界、重复结果和独立HPWL，最后把各次真实命令与检查结果保存到 `acceptance.json`。原输入文件还会进行前后摘要比对，确认没有被改写。检查程序只用Python标准库。

本轮Windows四类单元测试共57组通过，Linux共58组通过，多出的一组为Linux专用的保存失败检查；命令行检查分别为19组、18组通过。三套真实电路在两个平台均通过，详见[开发进度](初始布局开发进度.md)中的实测表。单元测试的实际编译命令还保存于各平台的 `unit_tests.json`。

布局文件和报告写入不是一个不可分割的动作。如果位置文件已经保存、随后报告保存失败，程序会返回失败，但位置文件可能仍存在；不要仅凭文件存在就判断本次运行成功。程序只在全部步骤成功后打印 `SUCCESS`。
